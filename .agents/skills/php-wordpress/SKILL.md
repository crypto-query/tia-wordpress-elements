# PHP and WordPress

Verified against **PHP 8.5.9**, **WordPress 7.0.3**, **WPCS 3.4.1**, **PHP_CodeSniffer 3.13.6**, **PHPStan 2.2.8** and **PHP-CS-Fixer 3.95.18**.

WordPress 7.0 (May 2026) raised its minimum to **PHP 7.4** and recommends 8.3+. That minimum is the **floor**, and it is the single fact that shapes WordPress PHP: you develop on 8.5 and ship to 7.4, so the language ladder and the code you may actually write are different questions. Everything below assumes the floor is live unless a plugin declares `Requires PHP` higher.

## Working rules

**Install the official WordPress skills; this one covers PHP.** WordPress ships 18 maintained skills at `WordPress/agent-skills` (`npx skills add WordPress/agent-skills --list`), covering blocks, block themes, patterns, the REST API, the Interactivity and Abilities APIs, WP-CLI, Playground, Blueprints, performance, plugin-directory guidelines and repo triage. They own the WordPress *subsystems*; this skill owns the *language and toolchain*. The split is near-total: across ~10,000 upstream lines, PHPCS and WPCS get one passing mention, PER-CS and `Requires PHP` get none, and the escaping guidance is a 29-line file. `wp-phpstan` (349 lines) is the only genuine overlap — it is broader on stubs and repo inspection, [static-analysis.md](references/static-analysis.md) is deeper on the traps. Install upstream and reach for it instead of inventing block, REST or Interactivity patterns here. Note their own disclosure: those skills were generated by an LLM from the handbooks and are on their first revision, so verify before trusting a specific claim.

**Two style worlds. Pick by where the file lands.** PER-CS 3.0 (4 spaces, short arrays, braces on the next line for classes) governs standalone PHP — libraries, CLI tools, framework code. The WordPress Coding Standards (real tabs, `array()`, Yoda conditions, spaces inside parentheses) govern anything shipping into `wp-content`. They contradict each other on nearly every formatting rule, so a codebase picks one per directory and enforces it with the matching tool: PHP-CS-Fixer's `@PER-CS3.0` set, or PHPCS with WPCS. Never split the difference by hand.

**Use `--standard=WordPress`, never `WordPress-Extra`.** WPCS auto-includes every sniff in its package when you name the `WordPress` standard, and five sniffs appear in no ruleset XML at all — including `WordPress.Security.ValidatedSanitizedInput` and `WordPress.DB.DirectDatabaseQuery`. `WordPress-Extra` gets escaping and nonce checks but silently loses input validation. WPCS's own `phpcs.xml.dist.sample` makes exactly this mistake.

**Prove floor compatibility with per-version runtimes, not a config flag.** PHPStan's `phpVersion` setting (single value or `min`/`max` range) catches *type and syntax* features missing at the floor — `mixed` on 7.4 is flagged — but never function availability: `str_contains()` and `array_first()` pass clean under `phpVersion: 70400` because PHPStan reads the analysing runtime's function set. PHPCompatibility is no better; its stable release is 9.3.5 from December 2019 and knows nothing after PHP 7.4, so it waves through every PHP 8 function. What works is `https://api.phpstan.org/analyse`, which runs real 7.2–8.5 runtimes and reports per version — see [static-analysis.md](references/static-analysis.md).

**Let the sniff settle arguments about safety.** WPCS carries explicit lists of which functions count as escaping, as sanitizing, and as implicitly unslashing, and those lists are the operational definition — not intuition, not the handbook prose. When a reviewer and an author disagree about whether output is escaped, run `phpcs -s` and read the sniff name.

## Corrections to common assumptions

Training data on PHP is dominated by PHP 7 and pre-3.0 WPCS. Ordered by how often each one bites:

- **WordPress still bans short array syntax.** `[ 'a' => 1 ]` trips `Universal.Arrays.DisallowShortArraySyntax.Found` under WPCS 3.4.1. Tabs, Yoda conditions, spaces inside parentheses, and double-arrow alignment are all enforced too — modern-looking PHP fails WPCS on formatting alone while its types and namespaces pass untouched.
- **WPCS pins PHP_CodeSniffer 3.** WPCS 3.4.1 requires `squizlabs/php_codesniffer ^3.13.5`. PHPCS 4.0.4 exists and installs fine on its own, but not beside WPCS — Composer refuses the pair outright. `squizlabs/php_codesniffer` is still the canonical package name; `phpcsstandards/php_codesniffer` is marked abandoned *in favour of* it, which is the reverse of the usual direction.
- **At the 7.4 floor you get typed properties and arrow functions, and nothing newer.** Constructor promotion, `match`, union types and named arguments are 8.0; `readonly`, enums and `f(...)` are 8.1. `declare(strict_types=1)` is available and WPCS does not object to it, but it is not the WordPress default.
- **`static fn` is rejected in constant expressions.** PHP 8.5 allows closures in const expressions, but only `static function () {}` and first-class callables — `public const \Closure F = static fn ($s) => …;` is a fatal `Constant expression contains invalid operations`.
- **`clone with` on a readonly property only works inside class scope.** `clone($obj, ['x' => 1])` from outside throws `Cannot modify protected(set) readonly property … from global scope`; it has to live in a `withX()` method on the class.
- **Escaping does not survive a variable.** `$out = wp_kses_post( $x ); echo $out;` is flagged `EscapeOutput.OutputNotEscaped` — the sniff matches the escaping call at the point of output, so escape inline in the `echo`.
- **`wp_unslash()` is required unless the sanitizer is one of ten.** Only `absint`, `boolval`, `count`, `doubleval`, `floatval`, `intval`, `rest_sanitize_boolean`, `sanitize_key`, `sanitize_locale_name` and `sizeof` imply unslashing. `sanitize_text_field()` does not.
- **The dynamic `IN ()` idiom must be built inline.** Assigning the placeholder string to a variable first trips both `PreparedSQL.InterpolatedNotPrepared` and `PreparedSQLPlaceholders.UnfinishedPrepare`; the same expression inlined into `sprintf()` passes clean. Numbered placeholders (`%1$s`) are not quoted automatically, and spread arguments defeat the placeholder counter.
- **WordPress 7.0 stubs cannot be installed alongside `szepeviktor/phpstan-wordpress` 2.0.3**, which pins `php-stubs/wordpress-stubs ^6.6.2` and resolves 6.9.4 — one WordPress major behind.
- **`apply_filters()` is invisible to PHPStan even at level 9** — it returns *implicit* `mixed`, which only level 10 checks. A docblock above the call site turns its first `@param` type into the return type, so documenting a filter is what makes it analysable. `get_option()`, typed `mixed` in the stubs, is caught at 9.
- **PHPStan on WordPress exhausts memory at PHP's default 128M** — but only on a cold result cache, so it fails in CI and passes on your second local run. Pass `--memory-limit=1G`.
- **PHPStan's top level is 10**, not 9 and not `max`-as-a-number. Level 8 is where WordPress's nullable returns start biting (`get_post()` is `WP_Post|null`), level 9 where explicit `mixed` does.
